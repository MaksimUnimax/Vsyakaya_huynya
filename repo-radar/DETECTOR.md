# Repo Radar Detector v1

## Цель

Найти не просто репозиторий с плохим README, а **аномалию**: публичная витрина говорит мало, а внутреннее устройство показывает существенно более зрелую, необычную или амбициозную работу.

Мы не пытаемся доказать психологию автора. Мы ищем наблюдаемые следы, совместимые с поздней публикацией, public/private-разделением или сознательно малозаметной витриной.

## Основные сигналы

### A. Слабая публичная витрина

Сильные признаки:

- нейтральное имя: `core`, `runtime`, `workspace`, `platform`, `engine`, `service`, `lab` и подобные;
- пустой или очень общий description;
- topics отсутствуют;
- homepage отсутствует;
- мало stars/forks относительно объёма проекта;
- README либо отсутствует, либо намного беднее глубоких внутренних документов.

По отдельности эти признаки почти ничего не значат. Важна комбинация.

### B. Неестественная зрелость молодого public repo

Особенно интересны репозитории, созданные недавно, но уже имеющие:

- большое дерево кода;
- CI и несколько видов тестов;
- deployment/recovery/security;
- миграции, БД, очереди, auth или распределённые компоненты;
- архитектурные документы и ADR/decisions;
- версии `2.0`, `3.0`, `v5`, долгую историю решений;
- несколько законченных подсистем;
- benchmark/chaos/performance/security проверки.

Такое состояние может означать, что работа раньше жила где-то ещё. Но это НЕ доказательство private GitHub: источником мог быть локальный Git, GitLab, другой repo, импорт или заранее подготовленный snapshot.

### C. Прямые следы public/private-разделения

Самые сильные сигналы:

- `public mirror`, `published snapshot`, `source mirror`;
- фразы вроде `unpublished development work is not included`;
- публичный repo, внутри которого README/description называет его `private` или `internal`;
- OSS kernel с явно отделённым `premium` слоем;
- публично выложены только packages/crates/SDK, но не конечный продукт;
- восстановленная/reconstructed история вместо естественной commit-history;
- ссылки на закрытые/недоступные компоненты, внутренние connectors или private datasets.

### D. Разрыв между названием и реальной целью

Хороший кандидат: сверху `workspace`, а глубоко внутри оказывается, например:

- универсальная инженерная рабочая станция;
- система самопереписывающихся AI-агентов;
- собственный 3D-движок;
- новая модель распределённого хранения;
- инфраструктура алгоритмической торговли;
- научная система, пытающаяся заменить привычную архитектуру ИИ.

Главное — не категория проекта, а величина разрыва.

### E. Необычная теза

Дополнительный плюс, если автор пытается сломать привычное предположение, например:

- «ИИ должен сам менять собственный harness»;
- «ИИ надо строить как набор аналогов частей мозга»;
- «содержимое не надо хранить, достаточно рецепта его восстановления»;
- «вместо одного агента нужна целая организация агентов».

Чем громче теза, тем строже проверяем факты. Амбициозное заявление не равно работающему прорыву.

## Поисковая процедура

1. **Discovery.** Ищем свежие public repos по нейтральным именам и аномалиям размера/активности. Типовые семьи: `core`, `runtime`, `workspace`, `platform`, `engine`, `service`, `lab`, `foundation`, `kernel`, `system`.
2. **Metadata triage.** Смотрим дату создания, размер, stars/forks, description, topics, homepage, язык, активность.
3. **Surface check.** README + корень дерева. Если всё ясно и полностью прозрачно — обычно CONTROL/REJECT.
4. **Deep check.** Ищем `docs/`, `architecture`, `context`, `roadmap`, `decisions`, `ADR`, `design`, `research`, `benchmark`, `deploy`, `security`, `memory`, `agents`.
5. **Related-repo check.** Смотрим организацию/автора и связанные репо: иногда `core` — только открытая часть более крупной системы.
6. **Private/public evidence check.** Ищем прямые формулировки про mirror/snapshot/private/internal/premium/unpublished.
7. **Reality check.** Отделяем уже реализованное от roadmap, идеи и заявления автора.
8. **Log immediately.** Сразу заносим в `CANDIDATES.md`, даже если кандидат оказался неинтересным.

## Полезные поисковые шаблоны

Примеры GitHub repository search, которые можно комбинировать с периодом времени:

```text
core created:>=2026-07-01 stars:0..10
runtime created:>=2026-07-01 stars:0..10
workspace created:>=2026-07-01 stars:0..10
platform created:>=2026-07-01 stars:0..10
engine created:>=2026-07-01 stars:0..10
```

После metadata-triage полезнее искать внутри конкретного repo слова и файлы:

```text
private
internal
public mirror
unpublished
premium
architecture
roadmap
ADR
benchmark
migration
deploy
recovery
v2
v3
```

Не надо зацикливаться на этих словах: сильный кандидат может использовать совершенно другую лексику.

## Шкалы

Каждому серьёзному кандидату можно поставить 4 независимые оценки `0..5`.

### Непрозрачность

- `0` — название/description сразу точно объясняют проект.
- `5` — по публичной витрине почти невозможно догадаться о реальном масштабе/назначении.

### Зрелость

- `0` — идея/пустой шаблон.
- `5` — рабочая система с тестами, эксплуатацией, восстановлением, безопасностью и устойчивым развитием.

### Амбиция

- `0` — маленькая утилита.
- `5` — попытка переосмыслить рынок, класс продуктов или фундаментальную техническую модель.

### Evidence public/private

- `0` — никаких следов.
- `1` — только generic metadata.
- `2` — сильный разрыв витрины и внутреннего содержания.
- `3` — косвенные признаки отдельной непубличной разработки.
- `4` — автор прямо пишет о public snapshot/mirror/unpublished/private/premium слое.
- `5` — есть публично проверяемая история перехода/разделения, позволяющая восстановить, что именно и когда было вынесено наружу.

## Статусы журнала

- `STRONG` — сильный кандидат для дальнейшего разбора.
- `MEDIUM` — интересный, но один или несколько ключевых сигналов слабые.
- `WEAK` — аномалия есть, но пока мало содержания.
- `CONTROL` — полезный отрицательный пример: имя generic, но проект честно раскрыт и повторно его искать не нужно.

Статус `WATCHLIST` здесь не используется. Наблюдение — отдельное решение владельца и фиксируется только в `WATCHLIST.md`.

## Формат объяснения кандидата

Всегда сначала обычный русский язык:

**Что это:** одно-два предложения без жаргона.

**Зачем:** кому и какую проблему решает.

**Почему интересно:** что в идее необычного/масштабного.

**Почему попал в радар:** конкретные наблюдаемые признаки.

**Что неизвестно:** где мы только предполагаем или где заявления автора ещё надо проверять.

Только после этого — технические детали, если они реально помогают.

## Антидублирование

Перед новым глубоким разбором обязательно искать repo по exact `owner/name` в `CANDIDATES.md` и `WATCHLIST.md`.

Если уже есть:

- без новых сигналов — пропустить;
- если repo заметно изменился — обновить существующую запись и `last checked`;
- не создавать вторую карточку того же repo после rename: хранить aliases в одной записи.
