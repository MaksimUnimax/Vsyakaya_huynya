# Repo Radar Detector v2

## Цель

Ищем **публичные рабочие репозитории, которые сами являются реальной активной разработкой, но публичная витрина делает их заметно менее обнаружимыми или вводит в заблуждение относительно масштаба/назначения**.

Эталон класса: проект считается достаточно рабочим и ценным, чтобы его продолжали активно развивать в public, но repo оформлен так, чтобы случайный конкурент не понял по имени/description/topics, что внутри находится серьёзный продукт.

Ключевое слово здесь — **public**. Нам НЕ нужны проекты, у которых настоящая разработка private, а GitHub — только mirror/snapshot/CI projection.

Намерение чужого автора («прячется от конкурентов») нельзя объявлять фактом без прямого свидетельства. Мы фиксируем наблюдаемую маскировку/низкую обнаружимость и отдельно — возможное объяснение.

## Жёсткий фильтр target / off-target

### TARGET — `PUBLIC_CANONICAL_MASKED`

Кандидат должен по возможности одновременно удовлетворять следующим условиям:

- repo публичный;
- в нём идёт реальная активная разработка или он выглядит как основной рабочий source;
- repo не обозначен как read-only/public mirror/sanitized snapshot/CI projection чужого private source;
- имя/description/topics/homepage заметно хуже объясняют проект, чем его внутренние файлы;
- внутри обнаруживается зрелый, коммерчески интересный, необычный или существенно более крупный продукт;
- есть признаки длительной/системной разработки, а не одноразового demo dump.

### OFF-TARGET — не считать сильным кандидатом

Автоматически понижаем до `CONTROL/OFF_TARGET`, если:

- source of truth прямо указан как private/internal;
- GitHub нужен только для CI, release, installation, distribution или public snapshot;
- public repo является sanitised projection выбранных путей private repo;
- назначение продукта полностью и явно раскрыто в repo name/description/topics/README, даже если продукт очень интересный;
- это обычный open-source library/core с прозрачным назначением и без разрыва витрина↔содержание.

Private→public mirror может быть полезен как отдельное свидетельство практики публикации, но **это не наша цель поиска**.

## Основные сигналы маскировки

### A. Слабая/нейтральная публичная витрина

Сильные признаки:

- нейтральное имя: `core`, `runtime`, `workspace`, `platform`, `engine`, `service`, `lab`, `foundation`, `kernel`, `system`;
- имя вообще не связано с реальной отраслью/продуктом;
- пустой или бессодержательный description;
- topics отсутствуют или слишком общие;
- homepage отсутствует;
- мало stars/forks относительно зрелости и объёма проекта;
- README скромный, а глубокие docs/architecture/roadmap раскрывают намного больше;
- публичная организация/профиль почти не связывает repo с конечным продуктом.

По отдельности эти признаки ничего не доказывают. Нужна комбинация.

### B. Разрыв между витриной и реальной целью

Сильный кандидат: снаружи `workspace` / `core` / `runtime`, а внутри оказывается, например:

- полноценный коммерческий SaaS/control plane;
- узкоспециализированный продукт для дорогой отрасли;
- автономная AI-система;
- торговая/финансовая инфраструктура;
- собственная CAD/CAE/3D/robotics платформа;
- новая модель хранения/распределённых вычислений;
- зрелая система автоматизации бизнеса.

Чем сложнее догадаться о настоящем назначении по GitHub search result — тем лучше.

### C. Зрелость, плохо согласующаяся с витриной

Ищем:

- большое дерево кода;
- CI и несколько классов тестов;
- deployment/recovery/security;
- миграции, БД, очереди, auth, billing или distributed components;
- ADR/decisions/architecture/roadmap;
- версии `2.0`, `3.0`, `v5` и следы нескольких поколений дизайна;
- benchmark/chaos/performance/security checks;
- production runbooks, migrations, backups, packaging;
- серьёзный GUI/product surface при почти пустой GitHub-витрине.

Молодой public repo с такой зрелостью — дополнительный сигнал, что работа началась раньше, но источник прошлого нельзя выдумывать.

### D. Активное развитие

Важно отличать живой проект от случайного dump:

- свежие commits/pushes;
- последовательные feature branches/PRs/releases;
- развитие нескольких подсистем во времени;
- TODO/roadmap реально закрываются кодом;
- тесты и документация меняются вместе с продуктом.

Проект, который просто один раз выложили и бросили, менее интересен для нашей задачи.

## Срок разработки — обязательное поле

Для каждого серьёзного кандидата теперь указывать сроки настолько точно, насколько позволяет публичное evidence.

Нужно разделять три разных величины:

1. **Возраст текущего public repo** — от `created_at` GitHub до даты проверки.
2. **Публично наблюдаемая разработка** — от самого раннего доступного commit/release/tag/issue/документа, если это можно подтвердить.
3. **Фактическая разработка проекта** — только если внутренние документы, changelog, версии или автор прямо дают более раннюю дату. Если нет — писать `неизвестно`, а не приравнивать к возрасту repo.

Пример формата:

`Срок: public repo 8 месяцев; earliest verified project evidence ~14 месяцев; фактическое начало неизвестно.`

Особенно ценны проекты, которые выглядят зрелыми после многих месяцев/лет работы, но всё ещё остаются плохо обнаружимыми.

## Поисковая процедура

1. **Anti-duplicate.** Проверить exact `owner/name` во всех `repo-radar/CANDIDATES*.md` и `WATCHLIST.md`.
2. **Discovery.** Искать public repos по generic именам и низкой discoverability.
3. **Metadata triage.** Дата создания, push activity, размер, stars/forks, description, topics, homepage, язык.
4. **Canonicality check.** До глубокой оценки выяснить: это реальная public working repo или mirror/snapshot частного source. Mirror → CONTROL/OFF_TARGET.
5. **Surface check.** README + root. Если назначение сразу полностью очевидно — обычно CONTROL.
6. **Deep check.** `docs/`, `architecture`, `context`, `roadmap`, `decisions`, `ADR`, `design`, `research`, `benchmark`, `deploy`, `security`, `product`, `billing`, `migration`, `recovery`.
7. **Timeline check.** Найти earliest verifiable evidence и оценить срок разработки.
8. **Related-repo check.** Автор/организация/связанные repos; проверяем, не выдаёт ли другой repo настоящее название продукта.
9. **Reality check.** Отделять реализованное от roadmap и маркетинговых заявлений.
10. **Log immediately.** Реально разобранный repo заносить в очередной `CANDIDATES*.md`, включая reject/control, чтобы не повторять поиск.

## Полезные поисковые семейства

```text
core
runtime
workspace
platform
engine
service
foundation
kernel
system
backend
app

```

Главный фильтр — не само слово, а сочетание: generic surface + низкая известность + неожиданно серьёзное внутреннее содержание + активная public development.

После metadata triage полезны внутренние слова:

```text
architecture
roadmap
ADR

migration
deploy
recovery
security
billing
production
benchmark

```

Слова `private`, `public mirror`, `snapshot`, `projection`, `source of truth` теперь в первую очередь используются для **отсева off-target private-source mirrors**, а не как положительный сигнал.

## Шкалы

Каждому серьёзному target-кандидату ставим независимые оценки `0..5`.

### Маскировка / низкая обнаружимость

- `0` — search result сразу точно объясняет продукт.
- `5` — по имени/description/topics почти невозможно понять реальное назначение и ценность.

### Зрелость

- `0` — шаблон/идея.
- `5` — рабочая система с тестами, эксплуатацией, безопасностью, восстановлением и устойчивым развитием.

### Амбиция / коммерческая ценность

- `0` — маленькая утилита.
- `5` — крупный продукт, новая категория или потенциально существенное конкурентное преимущество.

### Уверенность, что repo — public working source

- `0` — явно private-source mirror/CI projection.
- `1` — почти наверняка snapshot/mirror.
- `2` — canonicality неясна.
- `3` — похоже на рабочий public source.
- `4` — активная естественная история разработки подтверждается.
- `5` — однозначно основной public development source по нескольким независимым признакам.

## Статусы журнала

- `STRONG` — хорошо соответствует `PUBLIC_CANONICAL_MASKED`.
- `MEDIUM` — похоже на target, но canonicality/маскировка/зрелость требует проверки.
- `WEAK` — слабая аномалия.
- `CONTROL` — полезный отрицательный пример.
- `OFF_TARGET_PRIVATE_SOURCE` — публичный mirror/snapshot/CI repo private-разработки; не тратить на него search budget нашей основной игры.

`WATCHLIST` назначает только владелец.

## Формат объяснения кандидата владельцу

Всегда сначала обычным русским языком:

**Что это:** что за продукт.

**Зачем:** какую реальную проблему решает.

**Срок разработки:** public age + earliest verified evidence + фактический срок, если известен.

**Почему похоже на маскировку:** конкретный разрыв между GitHub-витриной и содержанием.

**Почему может быть ценным:** зрелость/идея/рынок/техническое преимущество.

**Canonicality:** почему считаем, что это именно active public development repo, а не private-source mirror.

**Что неизвестно:** где остаётся гипотеза.

Намерение автора скрываться от конкурентов указывать только как гипотезу, если он сам этого не сказал.

## Антидублирование

Перед новым глубоким разбором обязательно искать exact `owner/name` во **всех** `CANDIDATES*.md` и `WATCHLIST.md`.

Если уже есть:

- без новых сигналов — пропустить;
- если repo заметно изменился — обновить существующую запись и `last checked`;
- после rename не создавать вторую карточку: хранить aliases в одной записи.
