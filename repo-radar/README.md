# Repo Radar

Отдельная игровая/исследовательская линия: поиск **публичных рабочих GitHub-репозиториев**, которые снаружи выглядят скучно, нейтрально, непонятно или непропорционально скромно, а внутри содержат заметно более серьёзный, зрелый, необычный или коммерчески интересный проект.

Это НЕ часть основных исследований репозитория `Vsyakaya_huynya`. Каталог `repo-radar/` изолирован от `research/` и не должен менять, блокировать или переопределять основную работу.

## Что мы ищем

Главный target теперь зафиксирован жёстко: **`PUBLIC_CANONICAL_MASKED`**.

Нам нужен repo, который:

- реально public;
- сам используется как активная рабочая разработка или основной public source;
- остаётся малозаметным за счёт generic name, пустого/нейтрального description, отсутствия topics/homepage или сильного разрыва между витриной и реальным содержанием;
- внутри оказывается существенно более серьёзным, чем можно предположить по GitHub search result;
- развивается достаточно долго/системно, чтобы было видно: это не случайный demo dump.

Область любая: AI, инженерия, биотех, финансы, графика, CAD/CAE, robotics, distributed systems, science, storage, developer tools, business automation и т.д.

### Что НЕ является нашей целью

Public repo, который лишь зеркалит private/internal source для CI, установки, релизов или distribution, — **не target**, даже если схема сама по себе интересная. Такие находки остаются в журнале как `OFF_TARGET_PRIVATE_SOURCE`/CONTROL, чтобы второй раз на них не тратить время.

То же самое относится к открытым проектам, где repo name/description/topics сразу честно и полно раскрывают назначение: интересный продукт ≠ замаскированный продукт.

## Срок разработки

Для каждого серьёзного кандидата обязательно по возможности писать:

1. возраст текущего public repo;
2. earliest verified public project evidence;
3. фактический срок разработки, если его можно подтвердить документацией/релизами/историей.

Если реальное начало неизвестно — так и писать. Молодой GitHub repo нельзя автоматически считать молодым проектом.

## Файлы

- `DETECTOR.md` — действующая методика поиска, фильтры target/off-target, шкалы и формат оценки.
- `CANDIDATES.md` и последующие `CANDIDATES*.md` — единый anti-duplicate журнал всех реально разобранных repo, включая отклонённые.
- `WATCHLIST.md` — проекты, за развитием которых следим. Добавление только по прямой команде владельца.
- `CLARIFICATION-2026-09-16.md` — переклассификация второго прохода после уточнения главного target.

## Anti-duplicate правило

Перед каждым новым поиском искать полное `owner/repo` **во всех** `repo-radar/CANDIDATES*.md` и `WATCHLIST.md`. Если repo уже записан, не делать повторный полный разбор без нового сильного сигнала, заметного развития или прямой команды владельца.

## Правило описания для владельца

Владелец проекта не программист. Для каждого серьёзного кандидата сначала объяснять простыми словами:

1. что это за штука;
2. зачем она нужна;
3. сколько по доступным данным над ней уже работают;
4. почему repo выглядит замаскированным/низкообнаружимым;
5. почему мы считаем именно этот public repo рабочим source, а не зеркалом private source;
6. почему проект может быть ценным/необычным;
7. что пока неизвестно.

Технические детали — после простого объяснения.

## Базовое правило честности

`generic name + empty description` не доказывает намеренную маскировку. `молодой repo + много кода` не доказывает прошлую private-разработку. Мы можем сказать: «поведение совместимо с попыткой снизить discoverability», но мотив автора объявляем фактом только при прямом публичном свидетельстве.

## Обновление

После каждого содержательного поиска:

- каждый реально просмотренный repo заносится в очередной `CANDIDATES*.md`;
- off-target/private-source mirrors тоже фиксируются как отрицательные примеры;
- повторно не исследуются без нового сигнала;
- пользователь сам решает, кого переносить в `WATCHLIST.md`;
- для watchlist при будущей проверке сравниваем состояние с датой прошлого просмотра, а не начинаем исследование с нуля.
