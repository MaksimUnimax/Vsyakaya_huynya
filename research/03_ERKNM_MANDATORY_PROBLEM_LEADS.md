# R3 — ЕРКНМ: проверки, нарушения и предписания как B2B-лиды

## Финальный статус

`KILL__DO_NOT_REOPEN_WITHOUT_NEW_EXTERNAL_EVIDENCE`

Дата решения: 2026-09-15.

Исходная модель R3 закрыта полностью: `R3A Upcoming Inspection`, `R3B Violation Found`, `R3C Prescription / Remediation`.

Полный архив причин закрытия и правила reopen: [`CLOSED_IDEAS_LEDGER.md`](CLOSED_IDEAS_LEDGER.md).

## Что мы пытались доказать

Исходная гипотеза была сильной именно по intent: официальное контрольное событие могло создавать обязательную, срочную и доказуемую потребность бизнеса.

Предполагались три коммерческих сигнала:

- `R3A`: будущая проверка -> продать подготовку к ней;
- `R3B`: официально выявлено нарушение -> продать услугу устранения;
- `R3C`: выдано предписание со сроком -> маршрутизировать лид профильному подрядчику.

На уровне идеи это было потенциально сильнее обычной базы компаний, потому что спрос должен был возникать из обязательного события, а не из косвенного предположения.

## Почему KILL

### Главный факт: проблема в режиме публичности, а не в API

Правила формирования и ведения ЕРКНМ прямо задают режим отображения каждого типа сведений:

- `1` — виден всем;
- `2` — виден только контролируемому лицу после авторизации;
- `3` — не виден до окончания события; после окончания виден всем.

Authority:
https://www.consultant.ru/document/cons_doc_LAW_382540/e0289c205d87c9146f87ba6a097c3c698db470b5/

Это фундаментально важнее наличия HTML, XML, CSV, XHR или undocumented endpoint.

### R3A — Upcoming Inspection Lead: KILL

Для исходной механики требовалось до проверки одновременно знать:

`конкретная компания/объект -> конкретное мероприятие -> дата будущей проверки`.

Критичные сведения о контролируемом лице/объекте относятся к режиму, который не даёт публичному внешнему продавцу нужную идентификацию клиента в коммерческое окно до завершения события.

Следствие: сценарий вида

`МЧС -> ресторан X -> проверка через 21 день -> лид пожарной компании`

не образует открытый массовый lead-feed в нужный момент.

### R3B — Violation Found Lead: KILL

Для этой модели требовался публичный поток:

`компания -> конкретно выявленное нарушение -> подходящий подрядчик`.

Сведения о результатах/нарушениях относятся к ограниченному режиму публичности. Коммерчески нужная детализация не образует открытый массовый поток для постороннего lead-provider.

### R3C — Prescription / Remediation Lead: KILL

Это была потенциально самая сильная подгипотеза:

`конкретная компания -> конкретное предписание -> срок исполнения -> профильный подрядчик`.

Но сведения о предписании и связанная actionable детализация также не дают публичному внешнему продавцу тот массовый открытый signal, ради которого строилась идея.

### Почему crawler или reverse engineering ничего не исправляют

Если нужное поле ограничено самим режимом публичности, то:

- новый XHR endpoint не создаёт коммерческий сигнал;
- browser automation не создаёт коммерческий сигнал;
- XML/CSV не создаёт коммерческий сигнал;
- LLM-classifier нарушений бессмысленно строить до появления публичных самих нарушений;
- старые исторические результаты не заменяют своевременный intent.

Поэтому R3 — не `BLOCKED`, а именно `KILL` исходной бизнес-модели.

## Не возвращаться к R3 из-за следующих аргументов

Не являются новым основанием:

- нашли удобный parser ЕРКНМ;
- появился undocumented API/XHR;
- можно скачать open-data;
- видна дата будущей проверки, но нельзя публично идентифицировать клиента в нужное время;
- можно классифицировать старые нарушения;
- можно собрать историческую базу завершённых проверок;
- можно сделать Telegram-бот по публичной части реестра.

Эти варианты не устраняют главный дефект — **нет открытого своевременного полного actionable lead**.

## Разрешённое условие REOPEN

Открывать R3 снова можно только при реальном внешнем изменении, например если нормативный режим или иной легальный официальный публичный источник начинает одновременно давать:

1. конкретное контролируемое лицо/объект;
2. событие достаточно рано для продажи;
3. конкретное нарушение/предписание и срок, если речь о remediation;
4. массовый регулярный доступ без авторизации от имени самой проверяемой компании.

До этого: `DO_NOT_REOPEN`.
