# Карта углублённого исследования коммерческих сигналов

## 1. Общая цель

Репозиторий создан для поиска небольших, практически проверяемых информационных бизнесов вокруг **ранних, редких или обязательных событий**, а не для преждевременного проектирования большого SaaS.

Нас интересуют сигналы, которые дают реальное информационное преимущество:

1. **Сигнал существует и доступен** — известны поля, задержка, стабильность и способ регулярного получения.
2. **Сигнал достаточно ранний** — возникает до того, как основная покупка/проблема уже решена.
3. **Сигнал квалифицирует реальную потребность** — не просто новая строка в реестре, а событие с коммерческим смыслом.
4. **Есть кому продавать** — конкретный покупатель лида с подходящим чеком/ценностью клиента.
5. **Остаётся конкурентное окно** — существующий игрок не выдаёт тот же результат проще, дешевле или раньше.

Отдельное ограничение, принятое после R1: **если жизнеспособность идеи требует дорогого платного Yandex Maps API как обязательной зависимости для валидации/MVP, такая реализация не рассматривается.**

## 2. Почему были выбраны именно R1 / R2 / R3

Это были три разные версии одной стратегии — искать официальный event, который рынок узнаёт слишком поздно или который создаёт обязательный спрос.

### R1 — Start-of-Activity Register

Тип преимущества: `EARLY_EVENT`.

Гипотеза: уведомление о начале деятельности по конкретному месту может появляться до фактического открытия и давать ранний лид.

Файл: [`01_START_OF_ACTIVITY_REGISTER.md`](01_START_OF_ACTIVITY_REGISTER.md).

Текущий статус: **исходная гипотеза частично опровергнута на live-данных**. Свежая запись ERVK не равна новой физической точке. R1 пока не закрыт целиком только из-за узкой отдельной гипотезы industrial/B2B events.

### R2 — Alcohol / HoReCa Early Signal

Тип преимущества: `HIGH_CONFIDENCE_VERTICAL_EVENT`.

Гипотеза: заявление/лицензирование алкоголя по конкретному объекту может давать более чистый ранний сигнал новой HoReCa-точки.

Файл: [`02_ALCOHOL_LICENSES_HORECA.md`](02_ALCOHOL_LICENSES_HORECA.md).

Финальный статус: `KILL__DO_NOT_REOPEN_WITHOUT_NEW_EXTERNAL_EVIDENCE`.

Причина в одном предложении: **лицензионный lifecycle структурно находится после start-of-activity события, ранний массовый публичный application-feed не доказан, а надёжно публичная лицензия слишком поздняя и легко копируется существующими data/HoReCa игроками.**

### R3 — ERKNM Mandatory-Problem Leads

Тип преимущества: `MANDATORY_INTENT_EVENT`.

Гипотеза: будущая проверка, нарушение или предписание создаёт обязательную/срочную покупаемую потребность.

Файл: [`03_ERKNM_MANDATORY_PROBLEM_LEADS.md`](03_ERKNM_MANDATORY_PROBLEM_LEADS.md).

Финальный статус: `KILL__DO_NOT_REOPEN_WITHOUT_NEW_EXTERNAL_EVIDENCE`.

Причина в одном предложении: **режим публичности ЕРКНМ не даёт внешнему продавцу своевременный открытый набор “конкретный клиент + будущая проверка / нарушение / предписание”, поэтому исходная lead-механика ломается фундаментально, а не технически.**

Архив закрытых идей и условия, при которых их вообще разрешено открыть снова: [`CLOSED_IDEAS_LEDGER.md`](CLOSED_IDEAS_LEDGER.md).

## 3. Единая методика для следующих идей

### A. Source authority

До продуктовых рассуждений установить:

- официальный источник;
- нормативную базу;
- кто и когда обязан вносить запись;
- реальные поля;
- timestamp события и timestamp публикации;
- историю/изменения;
- API / XML / CSV / XHR / HTML / browser-only доступ;
- режим публичности и ограничения повторного использования.

Наличие красивого UI не считается доказательством доступности данных, а наличие endpoint не считается доказательством коммерческой пригодности.

### B. Lead timing

Главный вопрос — не «есть ли запись», а **когда она возникает относительно момента покупки**.

Нужно измерять реальные интервалы, желательно median/P25/P75 и распределение по диапазонам.

Идея закрывается, если событие систематически появляется после того, как клиент уже выбрал основного поставщика/подрядчика.

### C. Signal quality

Каждый sample классифицируется минимум как:

- настоящий новый объект/потребность;
- существующий объект с изменением;
- административное переоформление;
- дубликат;
- событие без коммерческого смысла;
- unknown.

Нужна оценка precision, а не несколько красивых примеров.

### D. Buyer map

Для каждой вертикали:

- кто покупатель лида;
- что продаёт;
- типичный чек;
- когда принимается решение;
- стоимость нового клиента;
- нужен ли ЛПР/телефон или достаточно company + event;
- допустим ли такой outreach коммерчески и репутационно.

### E. Competition

Проверять не только SaaS:

1. прямые lead/data services;
2. СПАРК/Контур/Seldon/Rusprofile и другие агрегаторы;
3. CRM/enrichment/leadgen;
4. отраслевые базы и внутренние системы крупных покупателей;
5. агентства/ручные поставщики лидов.

Критический вопрос: **если мы докажем ценность нового источника, может ли уже существующий поставщик данных просто добавить его в свой pipeline быстрее, чем мы завоюем рынок?**

R1 + Parsing.agency показали, что новый источник сам по себе почти никогда не является moat.

### F. Unit economics

Считать:

- raw events/month;
- qualified events/month;
- стоимость добычи и enrichment;
- ручную долю;
- потенциальную цену лида/подписки;
- число реальных покупателей;
- стоимость acquisition этих покупателей.

Если для proof-of-value сначала нужен дорогой data API/инфраструктура — сильный минус идее.

### G. MVP boundary

Предпочтительны:

- Telegram;
- CSV/XLSX;
- периодический worker;
- простая продуктированная услуга;
- минимальный web/desktop слой.

Если ценность нельзя проверить без CRM, кабинетов, биллинга, multi-tenant backend и десятков интеграций — идея должна получить штраф ещё до разработки.

### H. Kill criteria

До исполнения фиксировать причины `KILL`, чтобы не защищать идею из-за потраченного времени:

- сигнал поздний;
- шум высокий;
- ключевые данные непубличны;
- доступ экономически неразумен;
- конкурент уже имеет distribution/history/source infrastructure;
- стоимость лида низкая;
- ручная квалификация съедает экономику;
- рынок узкий;
- источник легко копируется и не создаёт moat.

## 4. Evidence rule

Каждый существенный вывод получает статус:

- `VERIFIED_OFFICIAL`;
- `VERIFIED_MARKET`;
- `MEASURED`;
- `INTERVIEW_EVIDENCE`;
- `HYPOTHESIS`;
- `BROWSER_PROBE_REQUIRED`;
- `UNRESOLVED`.

Пробел в данных нельзя заменять догадкой.

## 5. Browser rule

Если обычный web/HTTP не читает источник полностью, это не означает, что данных нет.

Разрешён bounded read-only browser pass без обхода CAPTCHA, авторизации, геоблоков или антибот-защит. После browser readback факты должны быть перенесены в research/evidence.

Но browser/reverse engineering **не используется для спасения идеи**, если нужные данные ограничены самим нормативным режимом публичности.

## 7. Правило закрытых идей

Если идея попала в [`CLOSED_IDEAS_LEDGER.md`](CLOSED_IDEAS_LEDGER.md), её нельзя возвращать в backlog просто потому, что:

- прошёл срок;
- забылись детали;
- нашёлся новый parser/UI;
- идея получила новое название;
- кажется, что «можно попробовать ещё раз».

Для reopen нужен **новый внешний факт, который прямо уничтожает прежнюю kill-причину**.
