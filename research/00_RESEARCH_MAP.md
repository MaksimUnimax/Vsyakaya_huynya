# Карта углублённого исследования коммерческих сигналов

## 1. Общая цель

Исследуются три разные идеи, каждая как самостоятельный коммерческий продукт. Их нельзя преждевременно объединять в одну систему.

Для каждой идеи нужно доказать пять вещей:

1. **Сигнал существует и доступен** — какие именно поля публикуются, с какой задержкой, насколько стабильно и машиночитаемо.
2. **Сигнал возникает достаточно рано** — насколько раньше денежного события он появляется на практике.
3. **Сигнал квалифицирует реальную потребность** — можно ли отличить горячий потенциальный заказ от шума.
4. **Есть кому продавать** — конкретные категории покупателей, у которых стоимость одного нового клиента существенно выше стоимости сигнала.
5. **Конкуренция оставляет окно** — прямые и косвенные конкуренты не продают тот же результат дешевле/лучше/раньше.

## 2. Три независимых исследования

### R1 — Start-of-Activity Register

Источник: единый/официальный реестр уведомлений о начале предпринимательской деятельности.

Гипотеза: запись содержит не только факт существования ИП/ООО, а конкретное место деятельности, вид деятельности и заявленную дату начала. Это может позволить находить будущие точки бизнеса до фактического открытия.

Файл: `01_START_OF_ACTIVITY_REGISTER.md`.

### R2 — Alcohol / HoReCa Early Signal

Источник: заявления, решения и/или выданные алкогольные лицензии по конкретным местам деятельности.

Гипотеза: лицензирование может дать ранний или подтверждающий сигнал о новой HoReCa-точке.

Файл: `02_ALCOHOL_LICENSES_HORECA.md`.

### R3 — ERKNM Mandatory-Problem Leads

Источник: ЕРКНМ и связанные открытые данные о контрольных мероприятиях, результатах, нарушениях и предписаниях.

Гипотеза: назначенная проверка, выявленное нарушение или предписание создаёт обязательную/срочную потребность, которую можно преобразовать в квалифицированный B2B-лид для профильного подрядчика.

Файл: `03_ERKNM_MANDATORY_PROBLEM_LEADS.md`.

## 3. Единая методика

Для каждого исследования пройти восемь блоков.

### A. Source authority

Зафиксировать:

- официальный источник;
- нормативную базу;
- кто обязан вносить запись;
- момент возникновения записи;
- частоту обновления;
- все реальные поля;
- доступность истории/изменений;
- способы машинного доступа: API, XLS/XML/CSV, HTML, XHR/fetch, WebSocket, браузерный интерфейс;
- ограничения и условия повторного использования данных.

### B. Lead timing

Главный вопрос — не «есть ли запись», а **когда она возникает относительно момента покупки/обязательной траты клиента**.

Нужно измерять реальные интервалы, а не ссылаться только на нормативный срок.

Минимум:

- median;
- P25/P75;
- доля `same-day`;
- 1–3 дня;
- 4–7;
- 8–14;
- 15–30;
- 31–60;
- 60+.

Если официальная дата и фактическое событие различаются, строятся оба интервала.

### C. Signal quality

Каждая запись классифицируется минимум как:

- реально новый объект/потребность;
- существующий объект с изменением;
- переоформление;
- дубликат;
- событие без коммерческого смысла;
- неизвестно.

Нужно получить оценку precision: сколько сигналов из 100 действительно заслуживают передачи покупателю.

### D. Buyer map

Для каждой вертикали фиксировать:

- кто покупатель лида;
- что именно он продаёт;
- средний/типичный чек;
- когда принимается решение о покупке;
- насколько поздно/рано приходит наш сигнал;
- стоимость нового клиента для покупателя;
- нужен ли контакт ЛПР или достаточно компании+адреса+события;
- насколько хорошо источник позволяет персонализировать первое обращение.

Отдельно выбрать TOP-3 наиболее экономически сильных вертикали.

### E. Competition — обязательный самостоятельный блок

Проверять четыре уровня конкурентов:

1. **Прямые сервисы** — продают тот же сигнал/лид.
2. **Агрегаторы данных** — СПАРК, Контур.Фокус, Seldon, Rusprofile и аналоги, если позволяют построить тот же фильтр.
3. **CRM / lead-generation / enrichment** — если дают эквивалентный результат через другой источник.
4. **Ручные агентства/брокеры/отраслевые базы** — даже без SaaS, если фактически уже продают такие лиды.

Для каждого конкурента фиксировать:

- источник данных;
- задержку;
- географию;
- фильтры;
- поля;
- наличие контактов;
- Telegram/email/API/CRM;
- цену;
- эксклюзивность/неэксклюзивность;
- кому продаёт;
- главное преимущество;
- главное слабое место.

Нельзя делать вывод «конкурентов нет» только потому, что не найден SaaS.

### F. Unit economics

Посчитать минимум:

- сырых записей на выбранный город/регион за месяц;
- квалифицированных сигналов;
- число потенциальных покупателей таких лидов;
- допустимую цену одного лида;
- возможную подписку;
- вариант оплаты за лид;
- вариант эксклюзивной территории/категории;
- стоимость добычи/обогащения одного сигнала;
- необходимость ручной проверки.

### G. MVP boundary

Исходная цель — **не строить большой SaaS**.

Нужно отдельно ответить, можно ли проверить бизнес-модель как:

- Telegram-бот;
- периодический worker;
- desktop app;
- браузерное расширение;
- CSV/XLSX delivery;
- ручная продуктированная услуга поверх автоматического collector/scorer.

Если ценность нельзя проверить без CRM, кабинетов, биллинга, multi-tenant backend и десятков интеграций — это минус идее.

### H. Kill criteria

До начала разработки фиксируются условия `KILL`, чтобы не защищать идею из-за уже потраченного времени.

Общие kill-причины:

- сигнал появляется слишком поздно;
- высокий шум / низкий precision;
- официальный источник нестабилен или закрыт;
- машинное получение экономически неразумно;
- сильный конкурент уже даёт тот же сигнал раньше/дешевле;
- ценность одного лида слишком мала;
- покупателю всё равно нужен большой объём ручной квалификации;
- потенциальный рынок слишком мал.

## 4. Evidence rule

Каждый существенный вывод должен иметь один из статусов:

- `VERIFIED_OFFICIAL` — подтверждено официальным источником;
- `VERIFIED_MARKET` — подтверждено действующим коммерческим сервисом/рынком;
- `MEASURED` — посчитано на реальной выборке;
- `INTERVIEW_EVIDENCE` — подтверждено представителями целевого покупателя;
- `HYPOTHESIS` — пока только гипотеза;
- `BROWSER_PROBE_REQUIRED` — источник существует, но обычными инструментами не прочитан полностью;
- `UNRESOLVED` — критический вопрос без доказательства.

## 5. Browser / Work / Codex rule

Недоступность источника через обычный web/HTTP **не является основанием пропустить его**.

Если портал отдаёт 403, требует JavaScript, сложную форму, XHR, CAPTCHA-free browser session или динамический поиск:

1. зафиксировать точный пробел;
2. не делать вывод из отсутствия web-search результатов;
3. подготовить отдельный bounded prompt для ChatGPT Work или локального Codex с браузером;
4. потребовать read-only проход, network/DOM evidence, список полей и примеры записей;
5. запретить обход CAPTCHA, геоблоков, авторизации и антибот-защит;
6. после browser readback внести доказательства обратно в соответствующий research-файл.
