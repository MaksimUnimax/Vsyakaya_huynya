# Retail Deduction Recovery — Bounded Historical Sample Request

Дата: 2026-09-16

Назначение: готовая инструкция для qualified pilot participant после discovery call.

Это **не запрос полного доступа к ERP/1С** и не запрос production credentials.

## Что хотим проверить

На исторических данных за 3 месяца по **одной** федеральной сети проверить, можно ли автоматически и воспроизводимо обнаруживать только объективные расхождения между штрафом/удержанием сети и исходной EDI-цепочкой:

`ORDERS -> ORDRSP -> DESADV -> RECADV`.

Мы не будем автоматически решать юридические/качественные споры и не будем отправлять претензии от имени компании.

## Минимальный пакет

### 1. ORDERS

CSV/XLSX/XML export всех заказов и их версий за выбранный период.

Нужны поля, если доступны:

- id/номер заказа;
- версия/дата изменения;
- дата/время создания;
- дата/окно поставки;
- точка/РЦ;
- SKU/GTIN/внутренний код товара;
- заказанное количество;
- единица измерения;
- статус/отмена;
- цена строки — только если нужна для формулы штрафа.

### 2. ORDRSP

- номер ответа;
- id заказа;
- дата/время отправки;
- статус — подтверждён/изменён/отклонён/частично;
- SKU;
- подтверждённое количество;
- причина изменения/отказа, если есть.

### 3. DESADV

- id уведомления об отгрузке;
- id заказа;
- дата/время;
- shipment id;
- SKU;
- отгруженное количество.

### 4. RECADV

- id приёмки;
- id заказа/shipment;
- дата/время;
- SKU;
- принятое количество;
- отклонённое количество и причина, если есть.

### 5. Штрафы / удержания

За тот же период:

- штрафные акты/счета/реестр;
- id документа;
- дата;
- причина/code;
- сумма;
- ссылки на заказ/поставку/SKU, если они указаны;
- расчёт/formula text, если есть;
- deadline на возражение, если определён;
- итоговый статус.

PDF/XML/XLSX — любой исходный формат плюс таблица, если она уже есть.

### 6. Исторический исход

Если компания уже разбирала штраф:

- приняли / отклонили / оспорили / проигнорировали;
- исход;
- сколько отменили/вернули;
- приблизительно сколько времени ушло на разбор.

### 7. Только релевантные правила

Не нужен полный договор.

Нужны только пункты/приложения для 1–3 выбранных классов штрафов, например:

- недопоставка;
- подтверждение заказа;
- срок поставки;
- формула штрафа;
- срок/канал возражения.

## Что можно обезличить

Разрешено и желательно убрать:

- название supplier;
- ИНН;
- ФИО сотрудников;
- телефоны/email;
- данные конечных покупателей;
- банковские реквизиты;
- нерелевантные закупочные/финансовые документы.

Нужно сохранить стабильные pseudonymous IDs:

- supplier_sample_id;
- retailer/order/shipment/document ids;
- SKU id.

Без стабильных связующих id автоматическая сверка невозможна.

## Что не нужно передавать

- пароль/токен EDI;
- доступ к 1С;
- VPN;
- ЭЦП;
- банковский кабинет;
- полный договорной архив;
- кадровые данные;
- consumer PII.

## Какой результат вернём

По каждому штрафу:

- linked order/shipment;
- исходные EDI-события;
- deterministic class или `HUMAN_REVIEW`;
- конкретное расхождение;
- правило/формула;
- потенциально спорная сумма;
- отсутствующие доказательства;
- deadline/process risk.

Общий итог:

- total penalty RUB;
- Tier A penalty RUB;
- deterministic mismatch RUB;
- historical recovery;
- типовые причины;
- ручные трудозатраты;
- список классов, которые нельзя автоматизировать.

## Чего не обещаем

- что штраф «незаконный»;
- что сумма обязательно будет возвращена;
- юридическое заключение;
- автоматическую отправку претензии;
- решение quality/causation/Article-333 disputes.

## Минимальный useful sample

Если полный 3-month export тяжело получить, для первого технического теста достаточно:

- 20–50 штрафных документов;
- все связанные ORDERS/ORDRSP/DESADV/RECADV;
- 5–10 исторических кейсов с известным исходом;
- правила по одному penalty reason family.

Если даже такой bounded sample невозможно получить без длительного IT project, это само по себе важное negative evidence по DATA_TRUST/access gate.
